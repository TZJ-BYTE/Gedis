# RediGo 存储引擎重写评估

## 背景

这份文档用于整理当前 RediGo 存储引擎的主要问题，并回答两个核心问题：

1. 现有存储引擎是否还能继续作为长期基础演进。
2. 是否值得单独研发一套新的存储引擎，并以独立库的方式复用到其他项目。

结论先行：**重写存储引擎的想法是合理的**，但更适合走“独立引擎 + 渐进接入”的路线，而不是在现有 RediGo 内部继续大范围堆功能。

## 当前判断

现有实现已经具备可运行性，基础测试也能通过：

- `go test ./internal/persistence/...`
- `go test ./internal/database/...`

这说明它不是一个完全不可用的原型，但从工程结构看，它更接近“课程项目级、持续修系统债的引擎实现”，还没有达到“稳定可复用底座”的状态。

## 主要问题

### 1. 引擎级锁过重

`Put` 和 `Delete` 在引擎级别直接持有全局互斥锁，并把 WAL、vLog、MemTable 更新和 flush 判定都包进同一条临界区：

- `internal/persistence/lsm_engine.go:816`
- `internal/persistence/lsm_engine.go:1025`

这会带来两个后果：

- 写路径天然串行化，扩展性有限。
- 后续继续叠加能力时，锁竞争和长尾延迟会更难收敛。

### 2. 读路径锁粒度也偏粗

`Get` 在引擎级读锁内执行 MemTable 查找、SSTable 读取以及可能的 vLog 读取：

- `internal/persistence/lsm_engine.go:890`

这意味着慢读、磁盘读取或 value log 回源都会拉长锁持有时间，不利于高并发场景下的稳定性。

### 3. 配置接口与真实实现存在脱节

代码里暴露了不少配置项，但部分并没有真正进入关键路径：

- `UseBloomFilter` / `BloomFPRate` 定义在 `internal/persistence/options.go:40`
- 但 SSTable Builder 里 Bloom Filter 仍然直接硬编码为 `NewBloomFilter(10000, 0.001)`：
  `internal/persistence/sstable_builder.go:39`

类似地，`WriteAheadLog` 这个开关在配置里存在，但实际写路径仍然直接依赖 WAL。

这类问题说明当前引擎的“对外配置面”比“真正稳定的内部抽象”更大。

### 4. Compaction 和层级策略仍偏硬编码

当前 compaction 仍然以内建常量为主：

- `internal/persistence/compaction.go:17`
- `internal/persistence/compaction.go:20`
- `internal/persistence/compaction.go:23`
- `internal/persistence/compaction.go:26`

虽然部分阈值允许配置，但核心层级模型、容量增长方式和调度骨架仍然写死。这对“做成独立存储引擎库”不太友好。

### 5. 系统级问题修复记录本身就是信号

仓库已经专门维护了一份系统问题清单：

- `docs/system_issues_fix.md`

其中修过的内容包含：

- WAL 背压
- TableCache 并发安全关闭
- 清库后的回潮问题
- 持久化写成功语义
- vLog GC 的 CAS 语义

这说明当前引擎已经踩过不少正确性与长稳运行问题。它不是不能继续用，而是不适合再被当成“已经收敛的底层基座”。

## 是否值得重写

### 值得重写的场景

如果目标是下面这些事情，那么重写非常合理：

- 做一个真正独立的存储引擎，而不是 RediGo 的内部模块
- 希望未来给多个项目复用
- 希望未来暴露跨语言调用能力
- 希望重新梳理并发模型、恢复语义、文件格式和配置边界

### 不值得大改的场景

如果目标只是：

- 把当前 RediGo 做到可演示
- 补齐课程设计或论文答辩材料
- 做少量功能扩展

那继续在现有引擎上修补，成本通常更低。

## 语言选择建议

### 首选：Rust

适合做新的独立存储引擎核心，原因很直接：

- 比 C++ 更容易把内存安全和资源生命周期管住
- 适合实现 WAL、MemTable、SSTable、Iterator 这类底层组件
- 后续导出 C ABI 相对成熟，方便 Go / Python / Node / Java 复用

### 次选：Go

如果第一目标是快速接回 RediGo，而不是做最强跨语言底座，用 Go 重写也可以：

- 和现有项目集成成本低
- 迁移路径最短
- 但未来要做高质量跨语言封装时，边界通常不如 Rust 干净

### 不建议现在就上复杂多语言混编

“一个语言负责一部分核心能力”的方案理论上可行，但当前阶段收益不高，复杂度会先爆出来：

- 调试链路复杂
- 构建和发布流程变重
- ABI、内存所有权、错误传播都要额外设计

更现实的路线是：**先把核心引擎收敛到一种语言，再通过统一 ABI 暴露出去**。

## 关于 MinIO / 对象存储 offload

结论很明确：**不是必须，也不应该作为当前阶段的核心能力。**

原因：

- 单机 KV 的第一优先级应是正确性、恢复语义、读写路径和 compaction 收敛。
- 对象存储 offload 会显著增加系统复杂度，包括远端一致性、回源延迟、失败重试、监控和运维负担。
- 对当前项目来说，这块更像可选实验能力，不适合压在主 README 里当核心卖点。

因此，MinIO 最合适的定位应该是：

- 默认关闭
- 非核心路径
- 真有大容量冷数据需求时再启用

## 建议的落地路线

### 第一阶段：做最小可用引擎

先只做下面这些核心能力：

- WAL
- MemTable
- SSTable
- Manifest / VersionSet
- Recovery
- Compaction
- Iterator / Scan

不要在第一版就引入：

- vLog
- 热冷分层
- 对象存储 offload
- 太多策略参数

### 第二阶段：接回 RediGo

通过清晰适配层把新引擎接入 RediGo：

- 先保持命令层和协议层不变
- 只替换底层持久化实现
- 保持功能验证闭环

### 第三阶段：对外做成库

等引擎接口稳定后，再考虑：

- Go 直接嵌入
- 导出 C ABI
- Python / Rust / Node 等语言绑定

## 最终结论

你的判断不是“想太多”，而是比较准确地看到了当前存储引擎的阶段性上限。

对 RediGo 来说，现有引擎还能继续用来支撑演示、验证和局部迭代；  
但如果目标升级为“做自己的通用存储引擎底座”，那么单独重写一套更干净的实现，是一条更正确的路线。
